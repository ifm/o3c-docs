Migration Guide: O3R to O3C

Overview

The O3C is a stand-alone camera with on-board processing, offering built-in applications such as the Obstacle Detection System (ODS).

From an operational perspective, the O3C closely mirrors the O3R experience — configuration, parameterization, and application behavior remain largely consistent. However, the integrated architecture of the O3C introduces certain constraints compared to the O3R, such as reduced multi-camera scalability and limited computational headroom for simultaneous applications.

This guide highlights the key differences between the two platforms and provides step-by-step instructions to help you migrate your existing O3R-based setup to the O3C.

External Ego Data

Overview

On O3C, running full visual odometry inside the ODS application is not feasible because of limited compute resources. Therefore, ODS should be supplied with external ego-motion from the user application.

For the basic integration, send:

  • vx: longitudinal velocity in m/s

  • vy: lateral velocity in m/s

  • timestamp_ns: timestamp in nanoseconds

Time synchronization with the camera is not required for this interface.

Python Example

def send_velocity(self, vx: float, vy: float, timestamp_ns: int):
	"""Send ego-motion velocity (vx, vy, timestamp) to ODS."""

	# Ensure connected
	if not self.connected or not self._fg or not self._fg.is_running():
		if not self.connect():
			return False

	try:
		# Packet layout: little-endian float32, float32, uint64
		packet = struct.pack("<ffQ", float(vx), float(vy), int(timestamp_ns))
		cmd = SetTemporaryApplicationParameter(
			parameter=Parameter.ODS_MOTION_DATA,
			data=bytearray(packet)
		)
		self._fg.send_command(cmd)
		return True

	except Exception as e:
		logging.warning(f"send_velocity failed: {e}")
		self.connected = False
		return False

Conclusion

Migrating from O3R to O3C is straightforward at the API and parameterization level, but it is not a drop-in hardware-architecture replacement. The key adaptation is to treat O3C as an integrated edge device with tighter compute and interface constraints.

The most important migration deltas are:

  • ODS requires external ego data (vx, vy, timestamp_ns)

  • CAN interface is not available on O3C

  • On-device Docker workflow is not available on O3C

  • 2D defaults and 3D mode availability differ from O3R

Go-Live Readiness Checklist

Before release, verify the following:

  • Hardware wiring is adapted (power, Ethernet, trigger, switching outputs)

  • Required O3C sensor and application parameters are updated

  • External ego data stream is stable and continuous in operation

  • ODS behavior is validated in representative scenes and speed ranges

  • Startup, reconnect, and long-run stability tests are completed

Acceptance Criteria

Define migration success with measurable checks:

  • Stable ODS detections in the target range of operation

  • No loss of external ego data updates during endurance testing

  • Expected false-positive and false-negative performance envelope is met

  • Recovery behavior after network interruptions is verified
